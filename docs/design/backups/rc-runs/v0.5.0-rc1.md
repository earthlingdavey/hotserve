# `v0.5.0-rc1` on Backblaze B2's S3 endpoint

The twelve checks of [release-candidate.md](../../../release-candidate.md),
run on 2026-11-02, by an agent working for the owner, through B2's
S3-compatible endpoint. Each check there says what B2 showed; this page
says how the run was set up, and where it left the guide. Its outputs
are not kept in the repository: they name the owner's box and buckets,
and every result that bears is quoted in the check.

## How it ran

- **The box:** the owner's, an arm64 Hetzner VPS on Debian 13, with
  the `.deb` from the `v0.5.0-rc1` release. Its one app was given
  `sqlite app.db` and `files uploads`: 501 MiB in all, a 101 MiB
  database and forty files of 10 MiB.
- **The off-box machine:** a `debian:13` container on the agent's
  machine, with restic 0.18, rclone 1.60, awscli 2.23 and
  backblaze-b2 3.19.
- **The buckets:** six, each made with a lifecycle rule. One keeps
  prior versions for one day (check 3's first step); the other five
  keep them for 180.
- **The keys:** made by the owner with `backblaze-b2 create-key
  --bucket <bucket> --duration 1209600 <name> <capabilities>`. Each
  reaches one bucket, and none may make or delete a bucket or a key.
  - The box's capabilities, `listBuckets,listFiles,readFiles,writeFiles`
    as [Backups](../../../backups.md#before-you-start-the-bucket-and-what-it-protects)
    gives them, for every key except three: two read-only ones
    (`listBuckets,listFiles,readFiles`), for checks 4 and 6, and one
    that adds `deleteFiles`, for check 3.
  - Check 10's key adds `--name-prefix rc-prefix/`.

## Where the run left the guide

- **Check 4:** the recovery copies read the attacked bucket with a
  read-only key of that bucket, and wrote with a key of the new bucket,
  as two rclone remotes over B2's own API. The guide's single remote
  with the account's key was not used: the owner keeps the master key.
- **Check 7:** the second box is the first one wiped: the package, restic
  and sqlite3 purged, both accounts and every hotserve directory
  removed, then three system accounts made before the package was
  installed again. The box repository is private, so its file at the
  commit the first box ran (checksum matched against the box's own
  record) was copied over, and `hotserve init` was run on it as the
  guide says. Three things were done by hand:
  - **The `backup` block:** added after `init`, since the box
    repository's file has none. The first box ran with the same edit.
  - **The secrets:** the first box's secrets key and the app's env
    file were put back, in place of a new key and `make rekey`.
  - **The deploy:** the app was deployed once with a local deploy key
    added for it and removed after; the app repository's workflow
    could not be run.
- **Check 9:** `v0.3.0-rc1` predates the box channel and refuses a
  Caddyfile with a `box` block or `box_webhook`. Two attempts were lost
  to it, and their repositories are left over in the bucket. The third
  ran the earlier release with those lines taken out. The refusals'
  exit codes were read after the move, with the box put back on its
  `b2:` file by hand.
